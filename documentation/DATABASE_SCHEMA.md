# Nanote — Database Schema (Room, version 3)

Room is the **index**, never the content store. Document content lives in
per-document `.nanote` JSON files (see `STORAGE_AND_BACKUP.md`); Room powers
library lists, search, tags, PDF full-text hits, bookmarks, reading
positions and the activity feed.

- Database class: `com.nanote.core.database.AppDatabase` (`nanote.db`)
- Location: `filesDir/databases/nanote.db`
- Exported schemas: `core/database/schemas/com.nanote.core.database.AppDatabase/`
  (`2.json`, `3.json`; schema export is wired via the KSP
  `room.schemaLocation` argument)
- Version history: **v1** (v1.0.0 initial) → **v2** (Part 1 foundation) →
  **v3** (Part 3 PDF/storage/search — current)

## Migration chain

`MIGRATION_1_2` then `MIGRATION_2_3`, both registered on the builder and
unit-tested in `core/database/src/test/.../MigrationTest.kt` (a hand-built
v1 database is upgraded step-by-step and validated by Room itself).
Migrations are non-destructive: every added column carries a default, so
no user data is ever rewritten or dropped.

## v1 → v2 (Part 1)

| Table | Change |
|---|---|
| `notes` | + `coverColor`, `icon`, `pageTemplate`, `pageOrientation`, `pageSize` (notebook presentation), `lastOpenedAt`, `sortOrder` |
| `folders` | + `parentId` (self-reference → nested folders), `createdAt`, `updatedAt` |
| `recent_activity` | **new** — append-only activity log, cascade on document delete |

## v2 → v3 (Part 3)

| Table | Change |
|---|---|
| `notes` | + `fileSizeBytes`, `sourceFileName` (imported-file metadata) |
| `tags` | **new** — `name` (PK), `color`, `createdAt` |
| `note_tags` | **new** — join table (noteId, tagName) PK, cascade both directions |
| `pdf_text_pages` | **new** — extracted PDF text per page (documentId, pageIndex, pdfPage, text), cascade |
| `pdf_bookmarks` | **new** — per-document page bookmarks, cascade |
| `reading_positions` | **new** — one row per document (page + zoom), cascade |
| `search_history` | **new** — recent queries (query PK, searchedAt) |

## Tables (v3, current)

### notes — the unified document index
| Column | Type | Notes |
|---|---|---|
| id | TEXT PK | document id = on-disk folder name |
| title | TEXT | |
| kind | TEXT | NOTEBOOK \| PDF |
| favorite | INTEGER | |
| folderId | TEXT? | FK folders(id), SET NULL |
| createdAt / updatedAt | INTEGER | epoch millis |
| pageCount | INTEGER | |
| coverColor, icon, pageTemplate, pageOrientation, pageSize | TEXT | notebook presentation (v2) |
| lastOpenedAt | INTEGER | (v2) |
| sortOrder | INTEGER | custom order (v2) |
| fileSizeBytes | INTEGER | (v3, imports) |
| sourceFileName | TEXT? | (v3, imports) |

Indexes: `lastOpenedAt`, `sortOrder`.

### folders — nested folders
`id` PK, `name`, `parentId` (self FK, SET NULL), `createdAt`, `updatedAt`.
Index on `parentId`. Deletion **lifts** children to the parent instead of
cascading — documents are never lost with a folder.

### recent_activity
`id` PK autoincrement, `documentId` FK cascade, `activityAction`
(CREATED/OPENED/RENAMED/DUPLICATED/IMPORTED/MOVED — `action` is a reserved
SQL word, hence the column name), `occurredAt`. Pruned to the latest 100.

### tags / note_tags
See v2→v3 above. Tag usage counts are aggregated with JOINs.

### pdf_text_pages
One row per PDF page of extracted text (built at import in the background
by `PdfTextIndexer`, rebuilt after page operations). Powers the home
screen's "matches inside PDF text" search group. **No OCR** — image-only
pages simply have no rows.

### pdf_bookmarks
User bookmarks on PDF pages: `id` PK, `documentId` FK cascade, `pageIndex`
(document page), `pdfPage` (source PDF page), `title`, `createdAt`.

### reading_positions
`documentId` PK + FK cascade, `pageIndex`, `zoomScale`, `savedAt`. Restored
when the document reopens.

### search_history
`query` PK, `searchedAt`. Recent-search chips with per-entry removal.

## DAO access
`NoteDao`, `FolderDao`, `RecentActivityDao`, `TagDao`, `PdfTextDao`,
`BookmarkDao`, `ReadingPositionDao`, `SearchHistoryDao` — all Flow-based
for reactive UI, with a `@RawQuery` dynamic filter (positional args only)
for library perspectives.

## What Part 4 changed

Nothing — the integration confirmed both development branches shared an
identical `MIGRATION_1_2`, so the merged schema is exactly Part 3's v3.
The Part 4 work re-committed the exported `2.json`/`3.json` schema files
(generated by KSP during the verified build) for release hygiene.
